# 去除生成痕迹

说明书、源码注释、code.zip 里的 README 和填写清单都按“人写的”标准交付。scripts/style_scan.py 会标出常见问题，最后仍要通读。

## 两条硬性要求

说明书、填写清单和 web-form.json 里的网页文本出现下面两类表达时，materials.py verify 直接报错，改完才能交付。README 和注释也按同样要求写。

1. 防御性语言。只写软件做什么、怎么操作、结果是什么，不替软件或材料辩护、免责、预先解释“它没有什么”。典型写法：
   - 免责与限定：“仅供参考/演示/参照”“不代表……”“不构成……”“以……为准”“如有出入”“不保证”“特此说明”。
   - 否认未实现能力或限定结果用途：“未实现的……”“尚未实现”“不涉及……”“当前版本不提供……”“暂不支持”“不提供公网账号”“软件没有用到人工智能、物联网……”“演示数据不能解释为真实成绩”“前端不自行决定得分”。
   - 安抚与预先辩解：“不会丢失”“不会乱码”“不会被覆盖”“无需担心”“请注意”“需要注意的是”“这是防错设计，不是故障”。
   改法：换成正面陈述，或直接删掉。“正常关闭不会丢失已经保存的内容”改为“点保存时内容就写入了硬盘，关闭后再打开仍在”；“中文不会乱码”改为“中文正常显示”；“本清单不代表已提交”整句删除；技术特点类别只写选中的那一项。
2. “不是……而是”式对比及其变体：“不是X，而是Y”“这不是……”“X而不是Y”“X而非Y”“不仅……而且/更/还”“与其说……不如说”。改为直接陈述 Y，必要时把 X 作为单独的事实另写一句。

真实存在的输入校验、错误提示和纠错步骤照常写，例如“器材少于 2 项时提示‘器材清单至少需包含 2 项’，补齐后再保存”“编号不能空”。运行环境和使用条件也照常写，例如“不需要联网”“不需要注册账号”“换电脑时不需要重新录入”，这些是使用者要知道的操作信息。判断标准：句子在告诉读者怎么用，就保留；句子在替软件说明“它没有什么、结果不能当什么用”，就删掉或改成正面陈述。

## 说明书

- 封面不加“本说明书面向……/适用于……”之类的小字，封面只放名称、版本和信息表。
- 不写口头安抚：如“不妨先点开看看”“放心修改”“讲起来更有底”。
- 不用“小提示：”“温馨提示”等标签，不用比喻（“总账本”“好帮手”），不加全书收尾的总结段或鼓励段。
- 少用三项并列凑整（“三种常见用法”“三个时点”），少用破折号和成串加粗。
- 小标题用名词短语（“签名的作用”“指导文本检查”），不用一串问句（“签名是什么，为什么要用”“主界面分为哪几块”）。常见问题一节里个别“启动不了怎么办”可以保留。
- 同一件事只在最相关的位置说一次，例如解压位置、时间格式、按顺序操作。
- 示例和数字必须按代码实际行为核对：评分结论、播报秒数、取哪个数值、有没有“重置”按钮等。写“X 会被判为 Y”之前，先对照判定代码确认。
- 删掉套话后页面出现大块空白时，用代码或示例数据里查得到的真实内容补（如某个实验各阶段写什么、状态取值有哪几种），或调整段落位置、图片尺寸；不要再写新的套话。

## 源码注释

改注释会改变源码行数，改完必须重新生成源程序鉴别材料并更新源程序量。

### 目标风格：像学生自己整理过的项目

整体感觉是一个大学生把自己的课程设计或个人项目做完后，顺手整理过一遍：目录清楚、命名规范、能跑能测，注释是写给自己和同学看的，读起来轻松。具体是：

- 注释少而且不均匀。复杂逻辑、数据格式、容易踩的坑多写一两句；界面布局、简单的增删改查、名字已经说清楚的函数基本不写。有的文件注释多，有的几乎没有，这很正常。
- 语气平实、偏口语，短句为主，可以用“免得”“跟着刷新”“先……再……”“撞号就再加 1”这类说法；少用“负责”“实现了”“核心”“标准化”“规范性”“主面板”等公文词。
- 文件头一句话或干脆不写；入口文件写一下怎么运行就够了。
- 分段标记简短，如 `# 左：日志列表`、`# 第一组示例数据`。
- 留下的文档字符串都有信息量：格式、返回值约定、默认值、为什么这样处理。

### 刻意的规整本身就是破绽

人写的代码很少处处对齐、处处齐全。下面这些“过于整齐”的特征一出现，整份代码就像生成的：

- 每个文件都有同样结构的多行文件头。
- 每个类、每个函数都有一行文档字符串，而且多半在复述函数名。
- 界面代码每一行控件前都有 `# 行0：……`、`# 行1：……`。
- 一列常量后面跟着对齐成一列的行尾注释。
- 每个功能区前都有一样的 `# ====` 或 `# ---- …… ----` 装饰线。

### 分寸

追求的是自然，代码质量保持原样：不故意写错别字，不加没用的 TODO、调试打印或网络用语，不删有用的说明。只改注释和文档字符串，代码逻辑、界面文字和变量名不动（界面文字出现在说明书截图里，改了就要重新截图）。

### 具体规则

- Python 3 文件不加 `# -*- coding: utf-8 -*-`。
- 文件头不写“XX模块 / 负责…… / 包含：1. 2. 3.”；需要时写一句说明这个文件管什么，或写清运行方式、数据格式。
- 不给每个函数写复述函数名的文档字符串（“导出实验项目列表到 CSV 文件”“构建左右分栏主工作区”）；保留讲清格式、约束、副作用和原因的那些。
- 不用 `# ====` 横幅、`# ---- 左侧：…… ----` 装饰线，不在界面代码里逐行标“行0：/第1行：”。
- 不在注释里写需求原话或风格用语（“质朴外观”“简洁大方”），不给每个常量写一条复述名字的行尾注释。
- 不用【】强调。检查有没有混进韩文、日文字符（如“상세”），这是典型的生成错误。
- 注释要说明“为什么”：如“按钮先 pack 到底部，窗口矮的时候才不会被表单挤出去”。

改写流程：先完整备份代码目录，只改注释和文档字符串；用 `style_scan.py --compare-ast 备份目录 代码目录` 确认代码逻辑未变；运行项目自带测试和自检；再 build、verify、package，并同步更新填写清单和 web-form.json 里的源程序量、页数和选页范围。

## code.zip 里的 README 与许可说明

- README 和代码一个调子，像学生给自己项目写的说明：怎么运行、有哪些功能、目录里都是什么，几十行足够；不用“一、二、三”大标题配加粗小标题，不写“开箱即用”“无需复杂框架”。
- 许可说明只写软件实际用到的组件；软著材料排版用的字体等制作过程信息不放进软件包。

## 填写清单

- 按 assets/checklist-template 的格式写，不满篇加粗，不用“切勿”“严格一致”等命令腔，开头不加“本清单不代表……”之类的免责句。
- 开发目的、主要功能、技术特点用平实的句子说软件做什么，少堆叠名词短语；字数仍用 check_web_form.py 核对。
- 不替用户写开发方式或工具使用方面的声明，只写“平台询问时由本人按实际情况填写”。
